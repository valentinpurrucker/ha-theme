# Home Assistant card and theme research

Research checked 2026-10-14. This note is an implementation guide for a reusable custom Lovelace card collection and matching theme, with a clean, compact visual direction informed by Mushroom and Bubble Card.

## Recommended v1 scope

Build one frontend resource with several focused `custom:` card types sharing an entity row, icon treatment, state labels, spacing, corner radius, and action handling. Favor restrained surfaces, clear hierarchy, compact controls, and generous touch targets. Keep domain controls familiar and let theme tokens change the whole system.

Suggested v1 cards:

| Card | Core behavior |
| --- | --- |
| `entity` / `sensor` | Name, icon, state, optional secondary attribute; read-only by default. Entity rows can optionally expose standard tap/hold/double-tap actions. |
| `light` | On/off, brightness when brightness-capable, and optional color temperature/color controls only when the entity supports those modes. |
| `climate` | Current and target temperature, +/- target adjustment, HVAC mode selection when supported, with optional humidity/preset details. |
| `media` | Artwork/title where present, play/pause and next/previous only when advertised; volume only when supported. |
| `cover` | Open/close/stop actions when supported, position slider when supported, optional tilt controls. Treat garage doors with deliberate interaction. |
| `fan` | On/off and speed/percentage or preset controls when supported. |
| `button` / `scene` | A reusable action tile. Scene activation is a one-way effect, so use an explicit scene/action affordance and never make a scene look like a toggle. |
| `chips` | Small summary/status/action pills suitable for the top of a dashboard or section. |
| `title` | Lightweight heading and optional subtitle for card groups. |
| `weather` | Compact current conditions first; defer forecast graphs and provider-specific details. |

The first seven cover the common entity domains requested and broadly overlap Mushroom's entity, light, climate, cover, fan, media and chips cards. Mushroom also provides title and template cards; Bubble's catalog groups button, media-player, cover, climate, pop-up, select, separator and stacks. These projects validate recognizable domain-specific cards and a compact family-wide language. Their main design lesson is to make common controls quick to scan and preserve a small set of repeated visual primitives, rather than inventing a new control metaphor for each domain.

## Current Home Assistant frontend contract

- A custom card is a browser custom element registered under a tag, referenced in Lovelace YAML as `type: custom:<tag>`. Load its JS module as a dashboard resource (typically `/hacsfiles/<resource>/<file>.js` for a HACS install, or `/local/<file>.js` for a manual install). The resource must load before the card appears in the picker.
- Implement `setConfig(config)` and throw an error for invalid required config; Home Assistant renders an error card. Read entity state from the supplied frontend context and handle missing, `unknown`, and `unavailable` state objects without throwing.
- Current frontend source (`src/data/context/index.ts`) defines context IDs and shapes as follows: `states` is the all-entity map keyed by entity ID; `services` is the available services map; `hassRegistries` holds entity/device/area/floor registries; `hassInternationalization` holds locale, localize and translation data; `hassApi` holds API methods; `hassConnection` holds connection state; `hassUi` holds themes and UI state; `hassConfig` holds core config/auth/user data; `hassFormatters` holds entity formatting helpers; `entities`, `devices`, `areas`, and `floors` are individual registries; `narrowViewport` and `reducedMotion` are booleans. The official external custom-card example uses a vanilla `context-request` event with `event.context = "states"`, `subscribe = true`, and a callback. Save its unsubscribe function and call it in `disconnectedCallback`. Prefer narrow contexts for state and formatting where practical; the grouping and keys come from the frontend's current source. The custom card also commonly receives a `hass` property; it remains a useful fallback for API calls and broad compatibility. Avoid duplicate subscriptions or polling.
- Context shapes relevant to the cards: `states[entityId]` is a Home Assistant state object (`entity_id`, string `state`, `attributes`, timestamps and context); `hassApi` includes `callService`, `callApi`, `callApiRaw`, `callWS`, `sendWS`, `fetchWithAuth`, and `hassUrl`; `hassFormatters` includes localized state/attribute/name formatting; `hassInternationalization` includes locale settings and `localize`. These let a card preserve the user's language, number/date format, timezone, and unit formatting rather than manually formatting raw states.
- `getCardSize()` controls masonry distribution; one size unit is about 50 px, and the default is 1 when omitted. `getGridOptions()` supports Sections view. Sections use a 12-column grid, 56 px row height and 8 px gap. Options include `rows`, `min_rows`, `max_rows`, `columns`, `min_columns`, `max_columns`; columns default to 12 and multiples of 3 (3/6/9/12) are recommended. Without the method, a custom card spans 12 columns and ignores rows. Choose compact defaults (commonly 6 columns for a standard tile, 12 for a broad control) and allow resizing where sensible.
- Add `static getConfigElement()` to provide an editor and optionally `static getStubConfig()` for a sensible starter config. The editor gets `hass` and `lovelace`; emit bubbling, composed `config-changed` with `event.detail = { config: newConfig }`. Register the type in `window.customCards` with at least `type` and `name`; include a description and documentation URL. Keep YAML configuration usable even if the editor cannot represent advanced fields.
- Current custom-card documentation also describes `getEntitySuggestion` (available since HA 2026.6) for domain-aware card picker suggestions. Suggest only when the entity domain/device features truly fit.
- Use HA's `hass-action` event for configurable standard card actions instead of custom click semantics. Set `event.detail = { config: actionConfig, action: "tap" | "hold" | "double_tap" }` and dispatch a bubbling, composed event. HA supports `more-info`, `toggle`, `perform-action`, `navigate`, `url`, `assist`, and `none` actions. A consistent default is tap `more-info` for an entity, with hold and double-tap disabled (`none`); power and media control buttons can have explicit direct control behavior. Do not silently assign `toggle` to a whole climate/media/cover card.
- If calling an action directly, use the frontend's `hass.callService(domain, service, data)` compatibility surface (the UI now calls services “actions”; the underlying frontend API terminology can still be `callService`). For user-configurable actions prefer standard HA action config / `hass-action`, as that retains native navigation, dialogs, and future behavior.

Primary references: [Custom card developer docs](https://developers.home-assistant.io/docs/frontend/custom-ui/custom-card/), [Frontend data and contexts](https://developers.home-assistant.io/docs/frontend/data/), [Frontend context source index](https://github.com/home-assistant/frontend/blob/dev/src/data/context/index.ts), [Registering resources](https://developers.home-assistant.io/docs/frontend/custom-ui/registering-resources/), [HA dashboard actions](https://www.home-assistant.io/dashboards/actions/), and [Services are now actions](https://developers.home-assistant.io/blog/2024/07/16/service-actions/).

## Sections, themes, and styling

Sections is the default dashboard view layout and arranges cards in a responsive grid; a card can be full-width or occupy configurable grid cells. Custom cards should supply `getGridOptions()` so their default composition feels intentional there, and `getCardSize()` for legacy masonry views. Theme a card via HA CSS custom properties instead of hard-coded colors: respect the active HA theme and define a small, documented token layer for surface, muted surface, primary text, secondary text, accent/on-accent, border, radius, spacing, and state colors. Give tokens fallback values so it remains legible without the companion theme.

The companion theme should be an ordinary frontend theme under `frontend: themes:` and may override HA's global CSS variables as well as this project's namespaced custom properties. Namespaced variables avoid collisions and make the visual system easy to restyle. Support both light and dark themes through HA's theme selection and contrast-aware semantic tokens. Section background/radius theming uses HA's `ha-section-background-color` and `ha-section-border-radius`; remember transparent card backgrounds can visually merge cards into section backgrounds.

Avoid relying on undocumented shadow-root selectors, brittle DOM traversal into HA's private card internals, global stylesheet injection, or `card-mod` as a runtime dependency. Shadow DOM and narrowly scoped styles make cards predictable; expose deliberate CSS variables for user overrides. Keep default effects subtle and motion reduced when `prefers-reduced-motion` is set.

References: [Sections view](https://www.home-assistant.io/dashboards/sections/), [Dashboard views](https://www.home-assistant.io/dashboards/views/), [Frontend integration and themes](https://www.home-assistant.io/integrations/frontend/), [Frontend design guidance](https://developers.home-assistant.io/docs/frontend/design/).

## Feature-aware domain implementation

Use the entity's domain, state, attributes, and advertised feature/capability metadata. Do not infer capabilities from a model name or assume every entity of a domain has the same controls. Hide or disable a control if the corresponding feature is unavailable, and guard commands against missing entities. Current state data is the source of truth after an action; do not optimistically fake device state unless a control has a clearly temporary pending state.

- **Light:** `supported_color_modes` is the key capability list. `onoff` has no dimmer; `brightness` supports dimming; `color_temp` supports dimming and temperature; `white` is white-only without adjustable color temperature; color modes include `hs`, `rgb`, `rgbw`, `rgbww`, and `xy`. Brightness is an integer in 1..255. Effect/flash/transition are `LightEntityFeature` flags. A current color mode may be more restrictive during an effect, so use supported modes for the control set and current mode for displayed value. Avoid assuming every light supports color temperature or effects.
- **Climate:** `ClimateEntityFeature` flags gate target temperature, target humidity, fan mode, preset mode, swing mode, and turning on/off. HVAC modes and temperature bounds/step are entity attributes; honor `min_temp`, `max_temp`, `target_temp_step`, precision and unit. The frontend should use HA units/localization and avoid baking °C/°F assumptions into input increments. Temperature adjustment should send `climate.set_temperature` using the target temperature value and configured step.
- **Media player:** `MediaPlayerEntityFeature` includes browse/clear playlist/grouping, announce/enqueue, next/previous, pause/play, play media, repeat, search, seek and volume mute; volume set/step is available in current entity docs too. Show transport controls only for relevant flags and states. Volume may be unavailable; media title, artist, artwork, duration and position are optional attributes. Polling position locally is unnecessary; trust HA state updates.
- **Cover:** feature flags are `OPEN`, `CLOSE`, `SET_POSITION`, `SPEED`, `STOP`, `OPEN_TILT`, `CLOSE_TILT`, `SET_TILT_POSITION`, and `STOP_TILT`. Position values are 0 closed to 100 open. Treat `current_position` as optional and only show sliders when position control is supported. For garage covers, do not expose an accidental tap-to-toggle; make open/close explicit and avoid dangerous defaults.
- **Fan:** `FanEntityFeature` includes `SET_SPEED`, `OSCILLATE`, `DIRECTION`, `PRESET_MODE` and `TURN_OFF`/`TURN_ON` capability depending on current HA version/entity model. Modern fan entities can expose percentage or preset modes; render from actual attributes/capability metadata instead of expecting the legacy `speed` attribute. Only render oscillation/direction/preset controls when present.
- **Scene and button:** scene activation has no persistent on/off state; communicate it as an action. A generic button entity can represent a momentary action. Require a deliberate click target and preserve `more-info`/configured HA actions on the rest of the card.
- **Sensor/weather:** treat the primary state as text and display its unit from `unit_of_measurement`; never assume a numeric sensor. `unknown`, `unavailable`, missing units and stale updates need graceful rendering.

Primary entity references: [Light](https://developers.home-assistant.io/docs/core/entity/light/), [Climate](https://developers.home-assistant.io/docs/core/entity/climate/), [Media player](https://developers.home-assistant.io/docs/core/entity/media-player/), [Cover](https://developers.home-assistant.io/docs/core/entity/cover/), [Fan](https://developers.home-assistant.io/docs/core/entity/fan/), [Scene integration](https://www.home-assistant.io/integrations/scene/), [Sensor entity](https://developers.home-assistant.io/docs/core/entity/sensor/).

## Common card needs and interaction defaults

1. Every card needs an entity selector, entity validation, a useful name/icon fallback, state rendering, and explicit handling for unavailable entities. Preserve friendly name/icon/device class when users have not overridden them.
2. Allow optional `name`, `icon`, `secondary_info`, and a small action-config surface to be shared across types. Keep per-domain controls specialized; avoid a sprawling universal card schema in v1.
3. Make tap, hold, and double-tap behavior explicit in the shared API. Recommended defaults: read-only entity/sensor cards open more-info on tap; control cards put toggles/sliders/buttons on their own clear targets and use more-info when tapping the label/card body; hold and double tap default to none. Scene activation should be visually and spatially distinct from reversible toggles.
4. Use accessible native controls or HA components where stable: labels, keyboard focus, ARIA values/states, and touch targets matter especially on wall tablets. Sliders should show the value and only call supported actions.
5. Keep cards responsive: truncate long names safely, keep essential controls visible at narrow widths, avoid hover-only affordances, and expose sizing defaults that suit both Sections and Masonry.

## Defer from v1

Defer pop-up/navigation systems, card nesting and arbitrary layouts, CSS editor or raw style injection, community module/plugin stores, templating language, history graphs, advanced forecast charts, media browsing/search/queue management, cover tilt/speed controls unless validated on real devices, alarm/security/lock/vacuum/humidifier/person/calendar cards, entity aggregation, and custom backend integrations. These add API surface or device-specific complexity without being required to establish the core card family and theme.

## Reference projects

- [Mushroom Cards](https://github.com/piitaya/lovelace-mushroom): the README lists focused cards including chips, climate, cover, entity, fan, light, media, template and title, says all cards support the dashboard UI editor, and documents optional companion themes. Useful reference for compact domain cards, reusable entity visuals, editor coverage, and a restrained shared style.
- [Bubble Card](https://github.com/Clooos/Bubble-Card): its README lists button, media player, cover and climate alongside pop-up, select, separator and button stack; options are editable in HA's editor, with shared styling, templates, actions, and modules. Useful reference for pill/bubble silhouettes, compact control grouping, and deep customization. Treat pop-ups/modules/CSS templating as later scope rather than a v1 requirement.
